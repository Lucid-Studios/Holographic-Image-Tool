# Phase 4 Entry Criteria

This document defines the bounded bridge from the approved single-clock Phase 3 baseline into Phase 4 engrammatic work.

Its purpose is not to begin open-ended Phase 4 implementation. Its purpose is to define what may lawfully cascade forward now that Phase 3 has closed cleanly enough to be inherited.

## Current Status

The Phase 4 entry cascade opened on March 30, 2026 after the operator-approved Phase 3 release baseline was recorded.

That entry cascade currently authorizes:

- Phase 4 entry doctrine
- Milestone 1 validator-first engram scaffolding
- working-intent stance transitions for engram-support artifacts
- lawful and unlawful example planning and committed public-safe entry corpora
- capture-profile alignment for engram root and constructor evidence
- executable support-only perspectival and participatory entry sidecars with validator and inspection behavior
- committed lawful and unlawful Phase 4 reference artifacts with wrapper-backed corpus verification
- wrapper-backed Phase 4 support comparison for root coherence, branch coherence, counterfeit pressure, and lawful negative support states
- machine-checked Phase 4 transition markers for `intentClassification` and `supportShape`

It does not authorize:

- runtime identity behavior
- GEL or cGEL candidacy approval
- commitment, covenant, or formation logic
- OE or Sanctuary binding
- `.hogif` carrier implementation

## Purpose

Phase 4 should inherit stable temporal law rather than re-litigating it.

The entry cascade therefore exists to ensure that identity-bearing work begins from:

- the approved Phase 3 temporal baseline
- explicit evidence posture
- stable Prime-safe boundaries
- declared stop lines for stronger claims

## Interlaced Build Meaning

Inside the wider OAN build interlace, the current Phase 4 entry bridge should be read as a bounded support-evidence lane only.

It may strengthen:

- support-side validators
- inspection posture
- support comparison
- packet and doctrine readiness where admitted

It may not yet be treated as:

- candidacy approval
- commitment authority
- runtime identity law
- mandatory build dependence for the active executable lane

This boundary exists for a specific reason:

- the bridge is meant to make support evidence legible before stronger identity claims are even discussable
- the active executable stack has not admitted HDT as runtime identity authority
- first-run, certification, and later covenant-bearing semantics still live downstream of this lane
- skipping that boundary would turn evidence-of-identity into identity-by-assertion

## Entry Preconditions

Phase 4 entry work may proceed only while all of the following remain true:

- the Phase 3 single-clock release baseline remains stable and honestly documented
- temporal state classes and cross-artifact comparison semantics no longer drift between runs
- Prime-safe temporal inspection remains explainable without hidden normalization
- committed reference artifacts remain public-safe and mechanically verifiable
- Phase 3 Milestone 4 async and morphism work remains a governing dependency, not a silently active carrier implementation lane
- engram evidence is still treated as evidentiary support rather than constitutive identity authority

## Allowed Entry Work

The following work is in-bounds during Phase 4 entry:

- define Phase 4 Milestone 1 scope and acceptance criteria
- define a support-first stance ladder for working intent before Phase 5 decision semantics begin
- reserve validator-first schema and inspection boundaries for perspectival and participatory engram forms
- define lawful and unlawful example expectations
- align capture profiles with engram-root and constructor evidence
- define comparison and inspection questions that later validators must answer
- document stop lines between evidence, candidacy, commitment, and runtime life

## Not Yet Allowed

The following work remains out of bounds during Phase 4 entry:

- claiming that an artifact is itself a lawful engram admission
- equating candidate-support evidence with GEL or cGEL candidacy approval
- implementing runtime-bound identity continuity behavior
- binding Phase 4 artifacts into OE or Sanctuary chains
- introducing covenant, formation, acceptance, or commitment semantics
- weakening Prime-safe posture to make identity claims easier to inspect

## Research Best-Practice Alignment

Phase 4 entry should follow the same discipline already established in the local automation posture ladder:

- `Initial`: test bounded identity-form hypotheses without overclaiming
- `Formal`: define reproducible positive-path evidence for engram scaffolding
- `Closing`: define negative cases, counterfeit cases, and unsupported identity claims
- `Approved`: require explicit HITL approval before treating any Phase 4 baseline as adopted

This keeps identity-bearing work from skipping the evidence discipline that Phase 3 needed in order to close honestly.

## Stop Line

Do not treat Phase 4 as operationally underway until:

- Milestone 1 validator-first scaffolding is written and accepted
- at least one lawful and one unlawful entry example class are defined
- Prime-safe inspection posture remains coherent for engram-support artifacts
- the repo can distinguish evidence for candidacy from candidacy itself
- the repo can distinguish Phase 4 working-intent stances from later Phase 5 review and acceptance semantics
- working-intent stance markers are machine-checked rather than documentation-only
- operator review explicitly approves promotion beyond entry scaffolding
